# 1. Executive project goal

Design, build, test and deploy an integrated ERP platform that manages
the end-to-end operations and financial lifecycle of DriveCore's
vehicle-rental business.

The platform will consist of:

1.  **Web ERP:** Next.js application for management, administration,
    finance, sales, operations, maintenance and other authorised staff.
2.  **Driver mobile application:** React Native/Expo application for
    assigned jobs, vehicle handover, return inspections, photographs,
    mileage, fuel and incident reporting.
3.  **Shared backend:** Laravel REST API containing the authoritative
    business logic, workflows, permissions and integrations.
4.  **Central database:** PostgreSQL as the authoritative transactional
    data store.
5.  **Supporting infrastructure:** Redis, object storage, background
    workers, backups, monitoring and deployment configuration.

The central business principle from the SRS is:

> Enter information once and allow it to flow automatically across the
> relevant operational and financial modules.

Every vehicle must have both an operational history and a financial
history.

The completed system should enable management to determine:

-   The size, status and location of the fleet.
-   Who currently has each vehicle.
-   Which vehicles are available, reserved, rented, damaged or under
    maintenance.
-   Revenue and costs generated by each vehicle.
-   Vehicle utilisation, downtime and profitability.
-   Customer balances, overdue debts and collection status.
-   Maintenance due dates and repair history.
-   Expiring vehicle, driver, customer and contract documents.
-   Revenue, expenses, cash, receivables, payables and profit.

The system must reduce fragmented spreadsheets and manual duplication
while preserving traceability, security and financial control.

# 2. Project assumptions and planning boundaries

## 2.1 Team and capacity

The plan assumes two part-time developers:

-   **Frontend Developer:** React, JavaScript/TypeScript, Next.js and
    React Native/Expo.
-   **Backend Developer:** PHP, Laravel, JavaScript and PostgreSQL.
-   Both developers use **ChatGPT Codex** as an AI coding agent.
-   GitHub is the source of truth for code, issues, pull requests and
    project tracking.
-   Planning assumption: approximately 15--20 hours per developer per
    week. Confirm actual availability.

Codex assists with implementation, investigation, tests and reviews. It
does not replace human decisions, client approvals, security review or
acceptance testing.

## 2.2 Target schedule

Use **12--18 months** as the initial planning range for a controlled
production release, assuming:

-   The team maintains the assumed weekly capacity.
-   DriveCore provides timely access to decision-makers.
-   Business rules are clarified before implementation.
-   Existing data can be obtained and cleaned.
-   Third-party providers supply usable APIs and credentials.
-   Scope changes are controlled.

This is an estimate, not a guaranteed contractual commitment. If the
actual scope, team capacity, data migration or integration complexity
differs, re-estimate.

The source SRS gives indicative estimates of: - MVP: 3--4 months. -
Operations: 2--3 months. - Integration: 2--3 months. - Intelligence:
future phase.

The roadmap below expands that outline into milestones and includes a
dedicated driver application, offline behaviour, integration testing and
production readiness.

## 2.3 Scope discipline

The SRS includes a broad enterprise scope. The team must not attempt
every module simultaneously.

Prioritise: 1. Core rental lifecycle. 2. Fleet operations and
maintenance. 3. Financial control and accounting. 4. Driver field
operations and integrations. 5. Migration, UAT, security and production
readiness. 6. Predictive maintenance and advanced intelligence only
after the core platform is stable.

A feature is not complete merely because a screen or database table
exists. It must work through its end-to-end workflow, enforce
permissions and business rules, and have tests.

-   PHP and Laravel
-   REST API
-   Laravel Sanctum, configured appropriately for web and mobile
    authentication

-   Spatie Laravel Permission

-   Linux server, initially Ubuntu Server LTS

database.

authoritative business logic.

project. Do not create a separate backend for the driver app.

## 7.2 Frontend implementation standards

-   Use TypeScript strict mode.
-   Follow established project conventions; do not add libraries without
    justification.
-   Use TanStack Query for server state and cache invalidation.
-   Use Zustand only for appropriate local UI state.
-   Use React Hook Form and Zod for form UX; backend validation remains
    authoritative.
-   Use generated API types/client where configured.
-   Handle loading, empty, error, success, forbidden and offline states.
-   Do not fabricate production metrics or data.
-   Do not calculate authoritative financial totals or rental prices in
    the UI.
-   Do not store sensitive identity or financial information in
    localStorage.
-   Use large touch targets and clear error messages in the driver app.
-   Do not silently discard offline submissions.
-   Ensure the user can see whether a submission is pending, syncing,
    synced or failed.

## 7.3 Frontend definition of done

A frontend issue is complete only when: - Approved acceptance criteria
are met. - API contract is followed. - Loading, empty, error and success
states are handled. - Permissions and statuses from the backend are
respected. - Relevant tests pass. - Typecheck and lint pass. - Supported
screen sizes/devices are checked. - No hardcoded business rule or secret
is introduced. - Documentation is updated. - Backend integration has
been demonstrated.

## 8.2 Backend implementation standards

-   Keep controllers thin.
-   Use Form Requests for input validation.
-   Use Policies for resource/action authorisation.
-   Use explicit Actions/Services for business operations.
-   Use API Resources for response formats.
-   Use database transactions for multi-step operations.
-   Use locks/constraints for concurrency-sensitive workflows.
-   Prevent duplicate allocation and overlapping reservations.
-   Use idempotency for retryable mobile sync and webhooks.
-   Use queues for slow/retryable processing.
-   Avoid N+1 queries.
-   Use database indexes based on query patterns.
-   Store monetary values using decimal or integer minor units; never
    binary floating point.
-   Preserve financial records through void/reversal/adjustment rather
    than destructive edits.
-   Never expose internal database structure accidentally as the public
    API.
-   Do not implement unapproved business rules.

## 8.3 Backend definition of done

A backend issue is complete only when: - Approved acceptance criteria
are met. - Migrations are tested and reviewed. - Validation and
authorisation are enforced server-side. - Business rules have an
approved source. - Transactions and concurrency are handled where
needed. - API responses and errors are documented. - Success, failure
and permission tests pass. - Audit and idempotency requirements are
implemented. - No secret or sensitive data is exposed. - OpenAPI and
technical documentation are updated. - CI passes.

# 12. Security, data integrity and audit rules

These rules apply to every developer and Codex task.

## Data integrity

-   Backend is authoritative.
-   Use transactions for multi-step business operations.
-   Use database constraints/locking for concurrency.
-   Validate all state transitions server-side.
-   Use idempotency for retryable operations.
-   Use decimal or integer minor units for money.
-   Store timestamps consistently, preferably UTC, and display in the
    configured business timezone.
-   Preserve traceability between operational transactions and financial
    records.

## Audit

-   Do not permanently delete important financial or operational
    records.
-   Use controlled void/reversal operations.
-   Record actor, timestamp, action, record and material before/after
    values.
-   Preserve approval requester, approver, date/time and approved
    values.
-   Keep posted journals immutable except through approved correction
    processes.

## Security

-   Enforce resource-level backend authorisation.
-   Test IDOR and cross-company/branch access.
-   Apply least privilege.
-   Require MFA for privileged users where supported.
-   Validate uploads server-side.
-   Keep secrets out of Git and logs.
-   Encrypt traffic and backups.
-   Restrict access to customer, driver, identity and financial
    documents.
-   Use synthetic or properly anonymised data for development.
-   Never provide production data or secrets to Codex.
-   No AI agent gets production access or deploy authority.
